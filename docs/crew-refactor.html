2 · Os oito defeitos, com endereço

  1. Um <input type=text> para tudo. CrewPage.tsx:135 — o contrato entrega valueType ('boolean' | 'integer' | 'enum' | 'reasoning_level' | 'string_list'…) e a UI descarta. Boolean vira digitar a palavra true; enum vira texto livre; a validação só chega depois do round-trip.
  2. O par role × runner está em dois lugares, e o legível é o read-only. A tabela Resolved routing mostra exatamente o que interessa e não deixa mexer; a edição mora em 36 campos com nome pontilhado.
  3. RoleRouteView é rico e a UI usa 3 de 9 campos. api.schema.ts:682 — prompts, requiresReadOnly, requiresNativeStructuredOutput, fallback, fallbackAbsent, reasoningClamped chegam prontos e são jogados fora. É a informação que faria o select saber o que oferecer.
  4. A lista de roles está hardcoded no frontend. crew-config.ts:4 ROLE_PATHS duplica ALL_WORKFLOW_ROLES (config.schema.ts:509). Role novo no backend nasce invisível no botão de template.
  5. O template "local-only" é a sua máquina virando feature. crew-config.ts:96 cria um runner chamado moe com contextWindow: 49152 e aponta os 9 roles pra ele. Nenhum outro usuário tem "moe".
  6. Escopo de projeto mostra campos que o projeto não pode sobrescrever. resolver.ts:8 — só 7 chaves top-level são overridable e 5 são próprias do projeto. O resto deveria sumir, não ficar cinza com "Global only" em letra miúda.
  7. O efeito é repetido 126 vezes e não é lido nenhuma. "next execution context" sob cada campo é ruído; ele só importa no momento de salvar, agregado.
  8. "Herdar" em português no meio de uma UI em inglês. CrewPage.tsx:135 — pequeno, mas é o sinal de que ninguém leu a tela como usuário.

O que fica intacto. src/app/config-editor.ts, a fila de escrita por path, a revisão sha256 com 409 em conflito, o catálogo como allowlist de escrita, o codec YAML que preserva chaves desconhecidas e o fato de UI e CLI passarem pelo mesmo use case. Isso é bom trabalho e não se toca — a proposta é toda de apresentação, mais dois furos de contrato listados na seção 5.

4 · As oito decisões de design

1. A tela tem uma tarefa, não um esquema

Crew responde "quem faz o quê com qual modelo". Recovery, forge, collaboration, review, git — 100 campos — vão para Advanced. Não somem; saem do caminho.

2. Runner é um card, não seis campos

Identidade, tipo, saúde, modelo e capacidades num objeto só. Add runner pergunta o tipo primeiro, porque o tipo decide quais campos existem: CLI pede command; endpoint pede baseUrl e apiKeyEnv.

3. O select só oferece o que resolve

requiresReadOnly e requiresNativeStructuredOutput já vêm no contrato. Um runner sem escrita aparece desabilitado no executor, com o motivo — em vez de virar erro depois do save.

4. "Resolve para" fica ao lado do que você escolheu

Configurado e resolvido na mesma linha. Clamp de effort, fallback e rota quebrada aparecem onde a decisão é tomada, não numa tabela no rodapé.

5. Herança é visível e reversível

Cada valor no escopo de projeto diz de onde veio (default / global / aqui) e oferece override ou reset. O que o projeto não pode sobrescrever não é renderizado.

6. Salvar é um ato, não 126 atos

Barra fixa com contagem, efeito agregado, diff real do YAML e o comando de CLI equivalente — a paridade que o rodapé já promete, agora visível e copiável.

7. Zero conteúdo pessoal no produto

Fora o template moe. Entra Add runner alimentado pelos tipos que o registry suporta — e presets viram um YAML que o usuário importa, não um botão hardcoded.

8. Caminho pontilhado é metadado

roles.planner.runner deixa de ser o label e vira legenda mono copiável — porque é o que se digita no CLI, não o que se lê na tela.

A dependência que destrava tudo é o /runner-types. Sem ele, "Add runner" volta a ser uma lista hardcoded no frontend — o mesmo defeito do template moe, com outra roupa. Com ele, adicionar um adapter novo no registry faz o formulário aparecer sozinho, que é a condição para outra pessoa usar o agent-flow com os agentes dela.
